第 11 章：Nginx 与 Docker Compose 集成部署 ​

本章目标：用 Docker Compose 编排「Nginx + 后端应用 + 数据存储」完整栈，掌握容器化下的配置注入、网络、扩缩容、HTTPS 与日志管理。 完成后可一键 docker compose up -d 启动整套环境，并理解容器化 Nginx 与裸机部署的差异。

11.1 为什么用 Docker Compose 部署 Nginx ​

维度裸机/systemdDocker Compose
环境一致性依赖宿主环境镜像固化，任何机器一致
多服务编排手动管理依赖顺序一键启动整套栈
配置分发scp/Ansiblebind mount 或镜像内置
扩缩容手动加机器/改配置--scale + 服务发现
适合单台高性能静态服务应用栈编排、CI/测试环境、中小生产

典型架构

核心原则：只有 nginx 容器发布端口到宿主机，后端服务全部走内部网络，不对外暴露。

11.2 最小示例：Nginx 静态站点 ​

yaml
# examples/docker-compose/docker-compose.yml（最简版片段）
services:
  web:
    image: nginx:1.26-alpine
    container_name: web
    ports:
      - "8080:80"
    volumes:
      # :ro 只读挂载，防止容器内误改配置
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./html:/usr/share/nginx/html:ro
    restart: unless-stopped

11.3 配置注入的两种方式 ​

方式优点缺点适用
bind mount（volumes: - ./conf:/etc/nginx/conf.d:ro）改配置不用重建镜像依赖宿主机文件存在开发、单机生产
自定义镜像（COPY 进镜像）不可变交付、可版本化每次改配置要构建CI/CD、多机生产

自定义镜像示例

dockerfile
# examples/docker-compose/Dockerfile
FROM nginx:1.26-alpine
# 固化配置与静态资源，镜像即交付物
COPY nginx/nginx.conf /etc/nginx/nginx.conf
COPY nginx/conf.d/ /etc/nginx/conf.d/
COPY html/ /usr/share/nginx/html/
# 构建期校验配置，失败则构建失败（左移排障）
RUN nginx -t

11.4 完整全栈编排示例（Nginx + 双后端 + Redis） ​

yaml
# examples/docker-compose/docker-compose.yml
name: nginx-stack

services:
  # --------------------------------------------------
  # 边缘层：唯一对外暴露端口
  # --------------------------------------------------
  nginx:
    image: nginx:1.26-alpine
    container_name: gateway
    ports:
      - "80:80"
      # - "443:443"    # HTTPS 见 11.6
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      # - /etc/letsencrypt:/etc/letsencrypt:ro   # 证书挂载（HTTPS 时启用）
    networks:
      - frontend
      - backend                     # 需要访问 app，必须同时加入 backend 网络
    depends_on:
      app:
        condition: service_healthy  # 等 app 健康检查通过再启动（见 11.4.2）
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1/healthz"]
      interval: 10s
      timeout: 3s
      retries: 3
    restart: unless-stopped

  # --------------------------------------------------
  # 应用层：不暴露端口，仅内部网络可达
  # --------------------------------------------------
  app:
    image: hashicorp/http-echo:1.0    # 演示用 echo 服务，生产换成你的应用镜像
    command: ["-text", "hello from app", "-listen", ":3000"]
    expose:
      - "3000"                        # expose 只对容器网络可见，不发布到宿主机
    networks:
      - backend
    environment:
      TZ: Asia/Shanghai
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:3000/"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 5s
    restart: unless-stopped
    deploy:
      replicas: 2                     # 声明 2 个副本（--scale 亦可）
      resources:
        limits:
          cpus: "0.5"
          memory: 128M

  # --------------------------------------------------
  # 数据层
  # --------------------------------------------------
  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    expose: ["6379"]
    networks:
      - backend
    volumes:
      - redis-data:/data              # 命名卷持久化
    restart: unless-stopped

networks:
  frontend:                           # 边缘网络
  backend:
    internal: true                    # ← 关键：禁止该网络访问外网，后端彻底隔离

volumes:
  redis-data:

11.4.1 Nginx 侧配置（含容器 DNS 关键技巧） ​

nginx
# examples/docker-compose/nginx/conf.d/app.conf
server {
    listen 80;
    server_name _;

    # Docker 内嵌 DNS（所有自定义网络的容器都可用服务名解析）
    # 注意：Nginx 默认只在启动时解析一次 upstream 域名！
    # app 容器重建后 IP 变化 → 缓存旧 IP → 502。
    # 解法：resolver + 变量形式的 proxy_pass，强制每次请求时解析。
    resolver 127.0.0.11 valid=5s ipv6=off;

    location /healthz {
        access_log off;
        return 200 "ok\n";
        add_header Content-Type text/plain;
    }

    location / {
        set $upstream http://app:3000;   # 变量形式 → 运行时走 resolver 解析
        proxy_pass $upstream;

        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 3s;
        proxy_read_timeout 30s;
    }
}

11.4.2 depends_on 的三种条件 ​

yaml
depends_on:
  app:
    condition: service_started        # 默认：进程启动即可（不保证就绪）
  redis:
    condition: service_healthy        # 等 healthcheck 通过（推荐）
  migration:
    condition: service_completed_successfully   # 等一次性任务跑完（如建表）

11.4.3 效果验证 ​

bash
# 1) 启动整套栈
docker compose up -d

# 2) 查看状态（注意 HEALTH 列）
docker compose ps

# 3) 验证代理链路
curl http://127.0.0.1/
# => hello from app

# 4) 多副本分发验证（http-echo 返回内容相同，用容器 ID 观察）
for i in {1..6}; do curl -s http://127.0.0.1/; done

# 5) 验证后端隔离：backend 网络 internal=true，容器无法出网
docker compose exec app wget -qO- --timeout=2 https://www.baidu.com || echo "OK: 后端网络已隔离"

# 6) 重建 app 验证 DNS 重解析（关键测试）
docker compose up -d --force-recreate app
curl http://127.0.0.1/    # 配置了 resolver，不会 502

11.5 扩缩容与服务发现 ​

bash
# 扩到 3 个 app 副本
docker compose up -d --scale app=3

# Docker DNS 会对 app 服务名轮询返回 3 个 IP
docker compose exec nginx nslookup app 127.0.0.11

注意两个事实

  1. --scale 与 container_name 冲突（容器名必须唯一），扩容时去掉 container_name
  2. 若用传统 upstream 块写死 server app:3000，Nginx 启动时只解析到一个 IP——多副本流量不会均衡。要么用 11.4.1 的 resolver 变量写法，要么引入动态 upstream 方案（如 Consul Template）

11.6 HTTPS 部署（证书挂载 + certbot sidecar） ​

yaml
services:
  nginx:
    image: nginx:1.26-alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - /etc/letsencrypt:/etc/letsencrypt:ro        # 宿主机证书只读挂载
      - certbot-webroot:/var/www/certbot            # ACME 挑战目录
    networks: [frontend, backend]

  certbot:
    image: certbot/certbot:latest
    volumes:
      - /etc/letsencrypt:/etc/letsencrypt           # 可写，负责续期
      - certbot-webroot:/var/www/certbot
    entrypoint: >
      sh -c "trap exit TERM;
      while :; do certbot renew --webroot -w /var/www/certbot --quiet;
      sleep 12h; done"
    restart: unless-stopped

volumes:
  certbot-webroot:

11.8 生产加固清单 ​

yaml
services:
  nginx:
    image: nginx:1.26-alpine
    restart: unless-stopped          # 崩溃自动拉起；unless-stopped 避免随 docker daemon 误启动
    read_only: true                  # 根文件系统只读
    tmpfs:                           # Nginx 运行必需的写入路径用内存盘
      - /var/cache/nginx
      - /var/run
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE             # 仅保留绑定 80/443 所需能力（非 root 镜像可连此项也去掉）
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 256M
        reservations:
          memory: 64M

11.9 常用命令速查 ​

操作命令
启动/重建docker compose up -d / up -d --build（配置或 Dockerfile 变了加 --build）
查看状态docker compose ps（注意 HEALTH 列）
查看日志docker compose logs -f [服务名]
配置校验docker compose exec nginx nginx -t
热重载docker compose exec nginx nginx -s reload
进容器排查docker compose exec nginx sh
扩容docker compose up -d --scale app=3
配置预检docker compose config（渲染并校验 compose 文件）
停止清理docker compose down（加 -v 连数据卷一起删，慎用）

本章小结 ​

  • 只有 nginx 发布端口，后端服务 expose + internal: true 网络彻底隔离
  • 容器 DNS 是第一坑：Nginx 启动时只解析一次 upstream 域名，用 resolver 127.0.0.11 + 变量形式 proxy_pass 解决
  • depends_on: service_healthy 解决启动顺序，运行期故障靠 proxy_next_upstream
  • 配置用 bind mount（开发）或自定义镜像 + 构建期 nginx -t（生产）
  • 日志走 stdout + json-file 轮转；续期证书后 exec nginx -s reload

常见坑 ​

  1. 容器内 127.0.0.1 指向容器自身（第 10 章案例 5）：代理宿主机服务用 host.docker.internal（Docker Desktop）或宿主机内网 IP（Linux 需 extra_hosts: ["host.docker.internal:host-gateway"]）
  2. app 重建后 502：未配 resolver，Nginx 缓存了旧 IP——本章 11.4.1 的解法
  3. 改了 bind mount 的配置但不生效：bind mount 只同步文件内容，Nginx 不会自动 reload，必须 exec nginx nginx -s reload
  4. 端口冲突：宿主机 80 被裸机 Nginx 占用 → docker compose ps 正常但 curl 不通，ss -lnt 确认实际监听进程
  5. macOS/Windows 上性能折损：Docker Desktop 的虚拟化层有网络/文件系统开销，压测与生产请在 Linux 进行
  6. 时区错乱：容器默认 UTC，日志时间对不上 → environment: TZ=Asia/Shanghai 或挂载 /etc/localtime:ro
