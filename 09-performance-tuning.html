第 9 章：性能调优参数详解 ​

本章目标：理解每个性能参数背后的原理，会按「压测 → 定位瓶颈 → 调参 → 复测」闭环优化。 完成后能将单机 Nginx 的并发能力从默认的数千提升到数万级。

9.1 调优方法论（先测量，再优化） ​

黄金法则：一次只改一个参数，压测验证，否则无法归因。

9.2 Nginx 层调优 ​

9.2.1 worker 进程与连接数 ​

nginx
# main 上下文
worker_processes auto;                    # 一般 = CPU 核数；静态服务可设 2×核数

# CPU 亲和性：把 worker 绑到固定核，减少上下文切换和缓存失效
# 4 核示例：
worker_cpu_affinity 0001 0010 0100 1000;
# auto 自动绑核（1.9.10+，推荐）：
# worker_cpu_affinity auto;

worker_rlimit_nofile 65535;               # 单 worker 可打开的最大 fd 数（突破系统默认值）

events {
    worker_connections 65535;             # 单 worker 最大连接数
    use epoll;
    multi_accept on;
}

容量计算公式

最大并发连接 = worker_processes × worker_connections
最大并发请求 ≈ 连接数 / 2（反向代理时每个请求占 2 个连接：客户端 + 上游）

约束条件：
1. worker_rlimit_nofile ≥ worker_connections + 静态文件 fd + 日志 fd
2. 系统级 ulimit（fs.file-max）≥ 总连接数
3. 内存：每个连接约 256B（连接结构体）+ buffer，10 万连接约需 100MB+

9.2.2 连接处理 ​

nginx
http {
    # ---- 客户端侧长连接 ----
    keepalive_timeout 65;          # 客户端长连接空闲超时（配合浏览器默认）
    keepalive_requests 10000;      # 单连接最大请求数后断开（防内存碎片化）

    # ---- 请求体与超时 ----
    client_body_timeout 10s;       # 读取请求体超时
    client_header_timeout 10s;     # 读取请求头超时（防慢速攻击 Slowloris）
    send_timeout 10s;              # 响应发送超时
    client_max_body_size 20m;      # 最大上传体积（API 站按需调整）

    # ---- 缓冲区（避免磁盘临时文件）----
    client_body_buffer_size 128k;  # 请求体缓冲区；超过则写临时文件
    client_header_buffer_size 1k;
    large_client_header_buffers 4 8k;   # 大 Header（如超长 Cookie/URI）
}

9.2.3 upstream 连接池（反向代理性能关键） ​

nginx
upstream backend {
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;

    keepalive 32;                  # ← 关键：每个 worker 保持到后端的长连接数
    keepalive_timeout 60s;         # 上游长连接空闲超时
    keepalive_requests 1000;       # 单连接最大请求数
}

server {
    location /api/ {
        proxy_pass http://backend/;

        # 使用上游长连接必须加这两行，否则退化为短连接
        proxy_http_version 1.1;
        proxy_set_header Connection "";

        # 代理缓冲：慢客户端不拖垮后端
        proxy_buffering on;
        proxy_buffer_size 8k;
        proxy_buffers 16 8k;
        proxy_busy_buffers_size 16k;
    }
}

为什么 upstream keepalive 重要

无 keepalive：每请求 1 次 TCP 三次握手 + 四次挥手到后端
  → 10000 QPS = 10000 次建连/秒 ≈ TIME_WAIT 堆积 + 后端 CPU 浪费

有 keepalive（32）：连接复用
  → 建连开销 ≈ 0，后端 CPU 降 20-40%，P99 延迟显著下降

9.2.4 完整调优配置示例 ​

nginx
# examples/tuning/nginx-tuned.conf
user nginx;
worker_processes auto;
worker_cpu_affinity auto;
worker_rlimit_nofile 65535;
error_log /var/log/nginx/error.log warn;
pid /run/nginx.pid;

events {
    worker_connections 65535;
    use epoll;
    multi_accept on;
}

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    # 日志（JSON + 缓冲，见第 8 章）
    log_format json_combined escape=json '{"time":"$time_iso8601","status":$status,"rt":$request_time}';
    access_log /var/log/nginx/access.log json_combined buffer=64k flush=5s;

    # 传输优化
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;

    # 连接管理
    keepalive_timeout 65;
    keepalive_requests 10000;
    client_body_timeout 10s;
    client_header_timeout 10s;
    send_timeout 10s;
    client_max_body_size 20m;

    # 打开文件缓存（静态站神器）
    open_file_cache max=10000 inactive=20s;   # 缓存 1 万个文件的 fd/元信息
    open_file_cache_valid 30s;                # 30 秒内认为有效
    open_file_cache_min_uses 2;               # 至少访问 2 次才缓存
    open_file_cache_errors on;                # 也缓存 404 错误

    # gzip（见第 6 章）
    gzip on;
    gzip_comp_level 6;
    gzip_min_length 1024;
    gzip_types text/plain text/css application/json application/javascript image/svg+xml;

    include /etc/nginx/conf.d/*.conf;
}

9.3 操作系统内核调优（Linux） ​

Nginx 的瓶颈经常不在 Nginx 而在内核 TCP 栈。

bash
# examples/tuning/sysctl-nginx.conf
# /etc/sysctl.d/99-nginx.conf

# ---- 文件描述符 ----
fs.file-max = 1048576                     # 系统级 fd 上限
fs.nr_open = 1048576                      # 单进程 fd 硬上限

# ---- TCP 连接队列 ----
net.core.somaxconn = 65535                # listen() backlog 上限（默认 128 太小！）
net.ipv4.tcp_max_syn_backlog = 65535      # SYN 半连接队列
net.core.netdev_max_backlog = 65535       # 网卡接收队列

# ---- TIME_WAIT 处理（高并发短连接必调）----
net.ipv4.tcp_fin_timeout = 15             # FIN 等待时间（默认 60s 太长）
net.ipv4.tcp_tw_reuse = 1                 # TIME_WAIT 连接复用（对出站连接安全）
# 注意：tcp_tw_recycle 已在 4.12 内核移除，不要再配置

# ---- 端口范围（出站连接用，反向代理重要）----
net.ipv4.ip_local_port_range = 1024 65535

# ---- TCP 缓冲区 ----
net.core.rmem_max = 16777216              # 接收缓冲最大 16MB
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216
net.ipv4.tcp_mtu_probing = 1              # 自动探测 MTU

# ---- keepalive 探测 ----
net.ipv4.tcp_keepalive_time = 600
net.ipv4.tcp_keepalive_intvl = 30
net.ipv4.tcp_keepalive_probes = 3

# ---- 其他 ----
net.ipv4.tcp_slow_start_after_idle = 0    # 关闭空闲后慢启动（长连接性能）
net.ipv4.tcp_no_metrics_save = 1          # 不保存 TCP 指标缓存

压测注意事项

  1. 压测机 ≠ 被测机（否则争抢 CPU）
  2. wrk 本身也会成为瓶颈：压测机也要调内核参数（端口范围、fd）
  3. 观察被测机 top：Nginx CPU 接近 100% 才是真实上限；没满说明瓶颈在别处
  4. 对比 RPS 的同时必须看 错误率 和 P99 延迟（只看 QPS 会误判）

症状定位命令大概率原因解法

9.6 调优检查清单（按优先级） ​

P0（必做）

  • [ ] worker_processes auto
  • [ ] worker_connections 65535 + worker_rlimit_nofile 65535
  • [ ] sendfile on; tcp_nopush on; tcp_nodelay on
  • [ ] upstream keepalive 32 + proxy_http_version 1.1 + Connection ""
  • [ ] net.core.somaxconn = 65535
  • [ ] 进程 fd 限制（limits.conf / systemd）

P1（高流量站点）

  • [ ] listen ... reuseport
  • [ ] open_file_cache（静态站）
  • [ ] gzip/brotli + gzip_static
  • [ ] 内核 TCP 缓冲与 TIME_WAIT 参数
  • [ ] access_log buffer=64k（或关静态资源日志）

P2（极致场景）

  • [ ] worker_cpu_affinity auto
  • [ ] aio threads + directio（大文件）
  • [ ] TLS 会话缓存 50m
  • [ ] conntrack 调大或绕过

本章小结 ​

  • 调优闭环：压测基线 → 定位瓶颈 → 单变量修改 → 复测
  • 三大高频瓶颈：fd 上限、连接未复用（upstream keepalive）、backlog 队列
  • Nginx 层看 worker_connections/rlimit_nofile；内核层看 somaxconn/file-max/TIME_WAIT
  • 指标看 QPS + P99 延迟 + 错误率，三者缺一不可

常见坑 ​

  1. 改了 worker_rlimit_nofile 但系统 limits.conf 没改：Nginx 只能降到系统 hard limit 以下，两头都要调
  2. upstream keepalive 忘了加 Connection 空头：默认 HTTP/1.0 + 短连接，连接池形同虚设
  3. 盲目调大 keepalive_timeout：长连接占着连接数不放，高并发下反噬；65s 是平衡点
  4. 压测机上没调端口范围：wrk 把压测机 28232 个临时端口打满，误报「Nginx 到瓶颈」
  5. reuseport 与 listen 指令混用：同一端口有的 server 加 reuseport 有的不加，行为未定义——全部加或全不加
