第 3 章：配置文件结构与常用指令 ​

本章目标：理解 nginx.conf 的层级语法，掌握核心指令含义，能独立写出最小可用的完整配置。 完成后可执行 nginx -t 通过语法校验并启动服务。

3.1 配置层级架构 ​

Nginx 配置是上下文驱动的（context-driven），而非顺序执行脚本。顶层到内层的嵌套关系如下：

nginx.conf
├── main（全局上下文）
│   ├── user
│   ├── worker_processes
│   ├── error_log
│   └── ...
├── events（连接处理模型）
│   ├── worker_connections
│   └── ...
├── http（HTTP 流量上下文）
│   ├── server（虚拟主机）
│       ├── listen
│       ├── server_name
│       ├── location（请求路由）
│       │   ├── root / alias
│       │   ├── index
│       │   ├── proxy_pass
│       │   └── ...
│       └── location / { ... }
│   └── server { ... }
├── stream（四层代理上下文，可选）
│   └── server { ... }

匹配规则优先级 ​

  1. 先匹配 IP:PORT（listen）
  2. 再按 server_name 精确匹配 → 通配符开头 → 通配符结尾 → 正则
  3. 最后按 location 规则匹配路径（= 精确 → ^~ 前缀 → 正则 → 普通前缀）

3.2 最小可用的 nginx.conf（带逐行中文注释） ​

nginx
# ============================================
# 示例：examples/basic/nginx.conf
# 最小可用配置，可直接启动并通过 nginx -t 校验
# ============================================

# --------------------------------------------------
# main 上下文：全局参数，影响整个 Nginx 进程
# --------------------------------------------------
user nginx;                       # 1. worker 子进程的运行用户，生产应设为专用用户，不要用 root
worker_processes auto;            # 2. worker 进程数；auto 自动匹配 CPU 核心数
error_log /var/log/nginx/error.log warn;  # 3. 全局错误日志路径与级别（debug/info/notice/warn/error）
pid /run/nginx.pid;               # 4. master 进程的 PID 文件路径，用于信号控制

# --------------------------------------------------
# events 上下文：决定 Nginx 如何处理连接
# --------------------------------------------------
events {
    worker_connections 1024;      # 5. 单个 worker 能同时保持的最大连接数
    use epoll;                    # 6. Linux 下事件模型；macOS 用 kqueue，Windows 用 select
    multi_accept on;              # 7. 当一个事件触发 accept 时，尽量一次性 accept 多个连接
}

# --------------------------------------------------
# http 上下文：HTTP 协议相关配置
# --------------------------------------------------
http {
    # ---- 包含 MIME 类型定义，确保浏览器正确解析文件类型 ----
    include /etc/nginx/mime.types;
    default_type application/octet-stream;  # 未知类型按二进制流处理

    # ---- 日志格式定义（本章后续详解） ----
    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';
    access_log /var/log/nginx/access.log main;

    # ---- 性能基础调优（第9章会深入） ----
    sendfile on;                  # 8. 零拷贝发送静态文件（内核空间直接发给网卡）
    tcp_nopush on;                # 9. 累积小数据包一次性发送，减少网络碎片
    tcp_nodelay on;               # 10. 小数据包立即发送，降低延迟（与 tcp_nopush 不冲突）

    # ---- 长连接设置 ----
    keepalive_timeout 65;         # 11. 客户端长连接空闲 65 秒后关闭
    types_hash_max_size 2048;     # 12. MIME 类型哈希表大小，避免配置过大时报 hash bucket 错误

    # ---- 引入额外配置 ----
    include /etc/nginx/conf.d/*.conf;  # 13. 按文件拆分虚拟主机，便于模块化维护
}

3.3 核心指令详解（main 上下文） ​

指令默认值说明坑
usernobodyworker 进程运行用户不要设为 root；静态文件需该用户有读取权限
worker_processes1worker 数量auto 几乎总是对的；IO 密集型可设 auto 或 CPU核数
worker_cpu_affinity无绑定 worker 到指定 CPU在 NUMA 机器上可减少跨节点访问，提升性能
error_loglogs/error.log全局错误日志日志级别设为 warn 或更高，避免 debug 撑爆磁盘
pidlogs/nginx.pidPID 文件确保目录可写，否则 nginx -s reload 无法工作
daemonon是否后台运行Docker 中通常设 off，让 PID 1 正确托管

3.4 核心指令详解（events 上下文） ​

指令默认值说明坑
worker_connections512单 worker 最大连接数总并发 ≈ worker × worker_connections / 2（每个请求需要上下行连接）
use自动探测事件模型Linux 选 epoll；BSD/macOS 选 kqueue；不要随便改
multi_acceptoff一次 accept 多个连接on 在高并发下有小幅性能提升
accept_mutexoff是否加锁竞争 acceptoff 配合 reuseport 是现代方案
accept_mutex_delay500ms加锁失败后再试间隔通常不需要调

worker_connections × worker_processes 的并发估算

总连接数上限 = worker_processes × worker_connections
总并发请求数 ≈ 总连接数 / 2    # 每个请求通常消耗 1 个客户端连接 + 1 个上游连接

示例：4 worker × 65535 = 262140 连接 ≈ 13 万并发请求

3.5 核心指令详解（http 上下文） ​

3.5.1 基础指令 ​

指令默认值说明注意
include—引入外部文件放 /etc/nginx/conf.d/ 下模块化，不要直接改主文件
default_typetext/plain默认 MIME设为 application/octet-stream 防止未知文件被浏览器解析为文本
sendfileoff零拷贝必须 on，磁盘文件经内核直接到网卡，减少用户态拷贝
tcp_nopushoffTCP_CORK与 sendfile on 一起用，等攒够一个包再发
tcp_nodelayoffTCP_NODELAY高并发且小包多时开，避免 Nagle 算法延迟
keepalive_timeout75s长连接空闲超时别设太大（消耗连接数）；也别设太小（频繁建连开销）
keepalive_requests1000单长连接最大请求数高 QPS 可调至 10000

3.5.2 root 与 alias 的区别（经典易混点） ​

nginx
# 请求 URL：/static/logo.png
# 实际磁盘路径：/var/www/static/logo.png

# root：URL 路径会附加在 root 后面
location /static {
    root /var/www;           # 拼接结果：/var/www/static/logo.png ← 额外多了一层 /static
}

# alias：root 的别名，location 前缀会被替换为 alias 值
location /static {
    alias /var/www/static/;  # 拼接结果：/var/www/static/logo.png ← 前缀被替换，无重复
}

重要陷阱

  • alias 路径必须以 / 结尾（alias /var/www/static/），否则会把 logo.png 拼成 staticlogo.png
  • root 结尾有无 / 无所谓，因为路径是拼接的
  • alias 所在 location 不能用正则结尾不带斜杠，行为会很诡异

3.5.3 index 与 try_files ​

nginx
# index：当请求是目录时，尝试返回的文件
location / {
    root /var/www;
    index index.html index.htm;  # 按顺序尝试，先 index.html 再 index.htm
}

# try_files：按顺序尝试多个文件，不存在则走最后一个 fallback
location / {
    root /var/www;
    # 1) 请求 /about 先看 /var/www/about
    # 2) 不存在则尝试 /var/www/about.html
    # 3) 仍不存在则回退到 /var/www/index.html（SPA 核心技巧）
    try_files $uri $uri.html $uri/ /index.html;
}

try_files 最后一个参数与前面语义不同

nginx
# 最后一个参数如果是路径，会触发内部重定向（重新进入 location 匹配）
try_files $uri $uri/ /index.html;      # 内部重定向到 /index.html（再走一次 location）

# 最后一个参数带 =404 表示直接返回 404
try_files $uri $uri/ =404;             # 都不存在直接返回 404

# 最后一个参数是代理地址
try_files $uri $uri/ @backend;         # @backend 是命名 location（见下）

3.5.4 命名 location（named location） ​

3.6 location 匹配规则（面试高频） ​

nginx
server {
    # 1. = 精确匹配，优先级最高，命中即停
    location = /exact {
        return 200 "exact match\n";
    }

    # 2. ^~ 前缀匹配，一旦命中，不再尝试后续正则
    location ^~ /static/ {
        root /var/www;
    }

    # 3. ~ 区分大小写的正则匹配（按配置文件中的顺序匹配）
    location ~ \.(gif|jpg|png)$ {
        root /var/www/images;
        expires 30d;
    }

    # 4. ~* 不区分大小写的正则匹配
    location ~* \.(css|js)$ {
        root /var/www/assets;
        expires 7d;
    }

    # 5. 无修饰符的普通前缀匹配（作为兜底）
    location / {
        proxy_pass http://127.0.0.1:3000;
    }
}

优先级总结（从高到低） ​

  1. = 精确匹配（终止）
  2. ^~ 前缀匹配（终止，不试正则）
  3. ~ / ~* 正则匹配（按配置文件出现顺序，第一个命中即停）
  4. 普通前缀匹配（取最长匹配的前缀）

记忆口诀：= 绝对 > ^~ 前缀强锁 > ~ 正则先命中者赢 > 普通前缀取最长。

本章小结 ​

  • 配置是「上下文」驱动的，不是脚本；理解 main → events → http → server → location 层级
  • root 拼接路径，alias 替换前缀；alias 必须带尾斜杠
  • location 匹配：= > ^~ > ~ > 普通前缀；^~ 可锁死正则，正则按文件顺序
  • 用 include 模块化拆分配置，nginx -T 可 dump 完整配置用于排查

常见坑 ​

  1. location /path 没写尾斜杠：location /api { proxy_pass ... } 会把 /api/v1 传给后端为 /api/v1，而 location /api/ { proxy_pass ... } 传给后端为 /v1，取决于后端路由设计
  2. try_files 最后一项被当作 URI：try_files $uri =404; 返回 404；try_files $uri /index.html; 会重定向到 /index.html
  3. 正则 location 中括号未转义：location ~ /api/[0-9]+ 需要把 [] 引起来或转义，否则 Nginx 解析报错
  4. 多个 server 监听同一 IP:PORT 时：Nginx 用 server_name 匹配，但如果请求 Host 头为空或没匹配上，会走第一个 listen 指令出现的 server（注意是「配置文件加载顺序」，不是代码书写顺序）
