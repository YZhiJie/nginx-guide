第 10 章：常见问题排查与解决方案 ​

本章目标：建立系统化的排障思路，快速定位并解决 Nginx 运行中的常见问题。 结构：排障方法论 → 错误码索引 → 场景案例 → 工具箱。

10.1 排障方法论（四步法） ​

排查顺序（按命中率排序）：

  1. tail -f /var/log/nginx/error.log —— 90% 的问题这里有答案
  2. nginx -t —— 配置语法问题
  3. curl -v 复现 —— 看完整请求响应
  4. ss -lnt / lsof -i —— 端口监听状态
  5. 访问日志中的 $upstream_* 变量 —— 区分 Nginx 问题 vs 后端问题

10.2 HTTP 错误码索引（高频 Top 8） ​

10.2.1 502 Bad Gateway（最常见） ​

含义：Nginx 无法从上游获取有效响应。

根因error.log 特征解决方案
后端进程挂了connect() failed (111: Connection refused)启动后端，加进程守护（systemd/supervisor）
后端端口错同上核对 upstream 端口与后端实际监听端口
后端监听 127.0.0.1 但 Nginx 在别的机器同上后端改绑 0.0.0.0 或内网 IP
SELinux 拦截connect() failed (13: Permission denied)setsebool -P httpd_can_network_connect 1
Unix socket 权限不足connect() to unix:... failed (13: Permission denied)socket 文件属组加入 nginx 用户
后端响应头过大upstream sent too big header调大 proxy_buffer_size 16k; proxy_buffers 8 16k;

快速定位：

bash
# 直接从 Nginx 服务器测后端
curl -v http://127.0.0.1:3000/health
# 通 → Nginx 配置问题；不通 → 后端问题

10.2.2 504 Gateway Timeout ​

含义：连上了后端，但响应太慢。

nginx
# 调大超时（但先确认后端为什么这么慢！）
proxy_connect_timeout 5s;
proxy_send_timeout 60s;
proxy_read_timeout 60s;    # 慢接口（报表/导出）单独 location 调大
1
2
3
4
bash
# 用日志变量区分建连慢还是响应慢
# urt（upstream_response_time）大 → 后端处理慢
# uct（upstream_connect_time）大 → 网络/后端 TCP 队列满
log_format timing '... rt=$request_time uct=$upstream_connect_time urt=$upstream_response_time';

10.2.3 403 Forbidden ​

根因排查解决
目录无索引文件且无 index 指令error.log: directory index of "/path/" is forbidden加 index index.html; 或 autoindex on;
文件权限error.log: open() failed (13: Permission denied)chmod -R o+r /var/www + 目录需 o+x
SELinux 上下文getenforce 为 Enforcingchcon -R -t httpd_sys_content_t /var/www
allow/deny 拦截检查配置调整白名单
bash
# 权限一键检查（nginx 用户视角）
sudo -u nginx stat /var/www/site/index.html
sudo -u nginx cat /var/www/site/index.html > /dev/null && echo OK

10.2.6 499 Client Closed Request ​

Nginx 特有码：客户端在响应完成前主动断开。通常不是 Nginx 问题：

  • 用户取消请求（正常）
  • 上游慢导致前端网关先超时（如 CDN 超时 < Nginx 超时）
  • 排查：看该 URI 的 $request_time 分布

10.2.7 429 / 503（限流触发） ​

nginx
# 自己配置的限流触发时会返回 503，可定制为 429
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
limit_req_status 429;

location /api/ {
    limit_req zone=api burst=20 nodelay;
}

10.3.2 reload 不生效 ​

ps aux | grep "worker process is shutting down"

# 长时间不退出（有慢请求/长连接挂着），可设 worker 退出超时

10.3.3 配置改了但没效果（排查清单） ​

  1. nginx -t 通过了吗？
  2. nginx -s reload 执行了吗？（不是 restart 的习惯性忽略）
  3. 改的文件真的被 include 了吗？（nginx -T | grep "你的配置"）
  4. 浏览器/CDN 缓存了吗？（curl -I 绕过浏览器验证）
  5. 是否有多个 server 匹配，请求落到了别的 server？（default_server 陷阱）

10.4 典型场景案例 ​

案例 1：上线后部分用户白屏，部分正常 ​

现象：A 地用户正常，B 地用户白屏。 排查：

bash
# 1) 检查是否有多个 server 监听同端口且配了不同 root
nginx -T | grep -B5 "listen 443"

# 2) B 地用户请求落到了默认 server（SNI 或 Host 不匹配）
# 在默认 server 加日志确认
1

5

根因：域名 m.example.com 未配置 server_name，落到 default_server。 修复：补全 server_name 或加泛域名。

案例 2：压测时 QPS 到 5000 就出现大量超时 ​

排查：

bash
ss -s | grep timewait        # TIME_WAIT 数万
dmesg | grep conntrack       # nf_conntrack: table full, dropping packet
1
2

根因：conntrack 表满，新连接被内核丢弃。 修复：

bash
sysctl -w net.netfilter.nf_conntrack_max=1048576
# 或纯静态服务直接禁用 conntrack（iptables -t raw -A PREROUTING -j NOTRACK）
1
2

案例 3：下载大文件时 Nginx 内存暴涨 ​

根因：proxy_buffering on 且响应巨大，缓冲区打满内存。 修复：

nginx
location /download/ {
    proxy_pass http://backend/;
    proxy_buffering off;            # 流式转发，不缓冲
    # 或 proxy_max_temp_file_size 0;（禁临时文件+限制内存）
}

案例 4：WebSocket 每隔 60 秒准时断开 ​

根因：proxy_read_timeout 默认 60s，无消息时空闲超时被切断。 修复：

nginx
location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;       # 配合应用层心跳（如 30s ping）
}

案例 5：Docker 中 Nginx 代理宿主机服务 502 ​

根因：容器内 127.0.0.1 指向容器自身。 修复：

nginx
# 用 host.docker.internal（Docker Desktop）或宿主机内网 IP

    server host.docker.internal:3000;
    resolver 127.0.0.11 valid=10s;    # Docker 内嵌 DNS，解决启动时解析失败
}

10.6 应急操作速查（生产救命用） ​

bash
# 1) 配置写错导致 reload 失败，回滚
cp /etc/nginx/conf.d/site.conf.bak /etc/nginx/conf.d/site.conf
nginx -t && nginx -s reload

# 2) 快速摘流（维护窗口）：返回 503 + 维护页
# 在 server 顶部加：
# return 503; + error_page 503 @maintenance;

# 3) 紧急限流（被攻击时）
# limit_req_zone $binary_remote_addr zone=emergency:10m rate=1r/s;

# 4) 封禁恶意 IP
# deny 1.2.3.4;  deny 5.6.7.0/24;  （放在 server 块顶部）

# 5) 查看当前活跃连接数
ss -tn state established '( dport = :80 or dport = :443 )' | wc -l

# 6) 平滑升级 Nginx 二进制（不丢请求）
kill -USR2 $(cat /run/nginx.pid)     # 启动新 master
kill -WINCH $(cat /run/nginx.pid.oldbin)  # 旧 worker 优雅退出
kill -QUIT $(cat /run/nginx.pid.oldbin)   # 旧 master 退出

10.7 预防性最佳实践（避免半夜救火） ​

  1. 配置版本化：所有 nginx 配置入 Git，每次变更可 diff 可回滚
  2. 变更三步走：nginx -t → 灰度一台 → 观察 5 分钟 → 全量 reload
  3. 必备监控：QPS、5xx 率、P99 延迟、活跃连接数、证书剩余天数
  4. 日志保留：access 至少 14 天，error 至少 30 天
  5. 定期演练：证书续期失败、后端全挂（STALE 缓存兜底）、机房切换

本章小结 ​

  • 排障四步：error_log → nginx -t → curl 复现 → 二分定位
  • 502 = 连不上后端；504 = 后端慢；403 = 权限/SELinux；404 = 路径拼接错
  • $upstream_connect_time vs $upstream_response_time 区分网络问题与后端问题
  • 生产救命命令：回滚、503 维护页、紧急限流、USR2 平滑升级
